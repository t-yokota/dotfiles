# Orchestrator Playbook

このプレイブックは「オーケストレータが強いモデルでなくても、強いモデルと同じ規律で回せる」ことを目的とする。判断を減らし、検証を機械化する。

## 役割モデル

| 役割 | 責務 | 禁止事項 |
|---|---|---|
| Orchestrator | 計画・振り分け・diff レビュー・コミット・進捗管理 | spec の無い設計作業の自己判断着手 |
| Designer | 設計・仕様裁定・spec 作成（強モデル or ユーザー協働） | — |
| Worker | spec/指示書に従う実装・テスト作成 | コミット / スコープ外の変更 / 設計判断 |
| Reviewer | 専用観点のレビュー（UI・セキュリティ等） | — |

**大原則: Orchestrator は「設計済み spec があるタスク」だけを自分またはWorkerで実行する。** spec が無い設計作業（モジュール分割・仕様の裁定・デザイン方針）に出会ったら、着手せずユーザーへ方針を提案する。これは能力の問題ではなく、設計判断の失敗コストが実装判断より一桁大きいため。

## 1. Spawn プロンプトのパッケージング規約

Worker への spawn プロンプトには必ず以下を含める（コールドスタートの再探索が最大の浪費）:

1. **タスクの一文要約** と、該当 spec / 指示書の**パス + セクション名**（丸ごと貼らない。Worker に読ませる）
2. **対象ファイルの絶対パス一覧**（触ってよいファイルを明示）
3. **完了条件**（実行するコマンドと期待結果。例: `npm run test` / `type-check` / `lint` 全パス）
4. **やらないことリスト**（コミットしない / 対象外ファイルを触らない / 設計変更しない / 落ちたテストの期待値を無断で書き換えない）
5. **報告フォーマット**: 変更ファイル一覧 + 実行したコマンドと結果（件数含む）+ 判断に迷った点

## 2. Worker 報告の検証（自己申告を信じない）

Worker の「完了しました」は主張であって証拠ではない。コミット前に Orchestrator が自分で:

- [ ] `git status` / `git diff --stat` で変更ファイルが spawn プロンプトの対象一覧と一致するか確認（スコープ逸脱検知）
- [ ] 完了条件のコマンドを**自分で再実行**（テスト件数が作業前より減っていないか。「全件パス」の全件が縮んでいる事故は頻出）
- [ ] diff を読む。チェック観点: 挙動不変タスクでロジックが変わっていないか / テストの期待値・skip が書き換わっていないか / 規約違反（any、マジックナンバー、console.*、store 直接変更）/ 無関係ファイルの整形ノイズ
- [ ] 報告と成果物の突合: 「N 件のテストを追加」→ 実際に N 件あるか

## 3. 2ストライク・テイクオーバー

- 同じ種類の失敗が 2 回続いた Worker には、3 回目の追加指示を出さない。Orchestrator が引き取る
- 引き取っても解決しない場合、または解決に設計変更が必要な場合はユーザーへエスカレーション（試行ログの要約付き）
- 連続する小タスクは新規 spawn せず同一 Worker に SendMessage で継続（コンテキスト再利用）

## 4. コミット規律

- **コミット権は Orchestrator のみ**。Worker はワーキングツリーの変更まで
- 1 タスク = 1 コミット。タスク外の修正（途中で見つけたバグ等）は別コミットに分離
- コミット前チェック: セクション 2 の検証全通過 + タスク管理ドキュメントの進捗更新を同コミットに含める（プロジェクト規約に従う）

## 5. エスカレーション基準（ユーザー確認が必要なもの）

- 仕様バグ: 実装と設計が矛盾し、どちらが正かをユーザーが決めるべきもの
- spec からの逸脱が必要になった場合（spec の前提が現物と食い違う等。spec を黙って読み替えない）
- 設計方針の変更・要件の不明点
- 外部公開・破壊的操作（force push、ファイル削除で復元困難なもの）

確認待ちでブロックされたら、質問を提示した上で**依存しない次のタスクへ進む**。

## 6. Spec の品質ゲート（Designer 向け）

新しい spec を書いたら、実装前に**ドライラン読解**をかける: 中位モデルの Worker に「この spec だけで実装できるか。曖昧点・現物との不一致・不足情報を列挙せよ（実装はしない）」と読ませ、出てきた曖昧点を spec に反映してから着手する。spec の良し悪しはこのテストで測る（書いた本人の自信では測らない）。

## 7. 役割ごとのモデル割り当て

モデル名は世代ごとに入れ替わるため、表は役割で読み、新世代が出たら割り当て列だけを更新する。

| 役割 | 必要な特性 | 現在の割り当て (2026-09) |
|---|---|---|
| 軽量ワーカー（軽いレビュー・分類・大量の subagent） | 安く速く十分な品質 | Haiku 4.5 |
| 機械的ワーカー（spec 駆動の実装・テスト作成・安全網のあるリファクタ） | コストあたりのコーディング品質 | Sonnet 5 |
| Orchestrator / 裁量のあるワーカー | 強いコーディング力と確実な検証 | Opus 5.5 |
| Designer（設計判断・spec 作成・曖昧さの裁定） | 最も深い推論 | Fable 5.1（利用可能な間）。不可なら Opus 5.5 + ユーザーによる spec レビュー |

- 「spec の密度 vs 実装面積」で振り分ける: 指示が短く編集面積が大きい → 安いワーカー。判断が重く編集面積が小さい → Orchestrator 自身。
- Designer 役が使えないときは Orchestrator に設計を即興させない。spec を先に書くか、ユーザーへエスカレーションする。
